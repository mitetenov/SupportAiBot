# Команда оператора `/ask`

Дата: 2026-08-21

## Задача

Когда бот заглушен активностью оператора, оператор теряет доступ к базе знаний: чтобы дать
пользователю статью из FAQ, ему приходится искать её самому и копировать руками. Нужна команда,
которой оператор просит ответ у ЛЛМ прямо из топика поддержки, а ответ уходит пользователю.

Сценарий: пользователь спрашивает, оператор отвечает вручную (бот заглушается на 30 минут).
Пользователь спрашивает снова — оператор пишет в топик `/ask как оплатить`, и пользователю
уходит ответ по FAQ, как если бы отвечал бот.

## Поведение

`/ask <вопрос>` в топике форум-группы поддержки:

1. `user_id` резолвится по `TopicMapping` — тем же запросом, что уже делает
   `handle_support_group_message`.
2. Вызывается `llm_client.chat(<вопрос>, user_id)` — штатный путь целиком: гибридный FAQ-поиск,
   история диалога этого пользователя, MCP-инструменты Remnawave под его Telegram ID, учёт токенов
   на него. Обмен пишется в `chat_history`, поэтому следующий ход бота видит его как свой.
3. Маркер `[ESCALATE]` снимается, текст уходит пользователю **как обычное сообщение бота**, без
   префикса «Поддержка:». Следом — иллюстрация из FAQ, если первая запись выдачи её называет и она
   ещё не отправлялась в этом диалоге.
4. Копия ответа постится в топик с заголовком `support.ask.header`, чтобы оператор видел
   отправленное.
5. `conversation_state.record_operator_reply(user_id)` — окно заглушки продлевается на 30 минут:
   диалог по-прежнему ведёт оператор.

Пока идёт запрос к модели, в чате пользователя работает индикатор «печатает».

### Крайние случаи

| Случай | Поведение |
|---|---|
| `/ask` без аргумента | `support.ask.usage` в топик, пользователю ничего |
| Ошибка ЛЛМ | `support.ask.error` в топик, пользователю ничего |
| `/askfoo`, `/asking` | Не команда — доставляется пользователю как обычный текст оператора |
| `/ask` вне топика | Не обрабатывается (у сообщения нет `message_thread_id`) |
| `/ask` в подписи к фото | Не обрабатывается: подпись не читается, медиа копируется целиком, как сейчас |
| Пустой ответ модели | `bot.llm.empty`, как в штатном пайплайне |

Штатное подтверждение `support.sent` для `/ask` не отправляется: копия ответа в топике сама по себе
подтверждает доставку.

Пробел в знаниях (`/gaps`) по запросу `/ask` не фиксируется. Формулировка оператора — не органический
запрос пользователя; учёт таких запросов исказит статистику пробелов, которая нужна для правки FAQ.

`conversation_state.record_query` тоже не вызывается: последним вопросом пользователя остаётся то,
что написал он сам, — это то, что нужно `/operator` для оценки пробела.

## Структура

Логика не помещается ни в `router.py`, ни в `command_handler.py` без размывания их назначения:
первый маршрутизирует, второй обслуживает пользовательские и админские команды в личном чате.

- **`app/bot/illustrations.py`** — `IllustrationSender`. Правило «отправить картинку первой
  FAQ-записи, не более одного раза за диалог» переезжает из приватного
  `UserMessagePipeline._send_illustration` в отдельный класс поверх `TelegramMessageSender` и
  `ConversationState`. Метод: `send_first(chat_id, user_id, faq_context) -> int | None` — возвращает
  id отправленного сообщения либо `None`. `UserMessagePipeline` делегирует ему.
- **`app/bot/operator_ask.py`** — `OperatorAskCommand`. `parse(text) -> str | None` вычленяет запрос,
  `handle(topic_id, user_id, query)` выполняет сценарий выше. Зависимости: `llm_client`, `sender`,
  `illustrations`, `conversation_state`, `typing_indicator`, `support_group_chat_id`.
- **`app/bot/router.py`** — в `handle_support_group_message` перед доставкой текста: если `parse`
  вернул запрос, отдать его в `handle` и выйти.
- **`app/constants.py`** — ключи `support.ask.usage`, `support.ask.header`, `support.ask.error`.
- **`app/main.py`** — сборка `IllustrationSender` и `OperatorAskCommand`, проброс в `setup_router`.
