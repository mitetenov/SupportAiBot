# Админские команды `/stats clear` и `/gaps clear`

Дата: 2026-08-21

## Задача

Ни `llm_token_usage`, ни `knowledge_gaps` ничем не чистятся: фоновые задачи
(`chat-history-eviction`, `rate-limiter-eviction`, `conversation-state-eviction`) их не трогают, TTL
нет. Данные копятся, пока админ не сходит в psql руками. Пробелы в знаниях особенно быстро теряют
смысл: запрос, по которому уже написана статья FAQ, продолжает висеть в топе `/gaps`.

## Поведение

- `/stats clear` — удаляет все строки `llm_token_usage`, отвечает числом удалённых записей.
- `/gaps clear` — удаляет все строки `knowledge_gaps`, отвечает числом удалённых записей.

Обе команды доступны только админам из `TELEGRAM_SUPPORT_ADMIN_TELEGRAM_IDS` и, как остальные
админские команды, работают только в личном чате с ботом.

Удаление необратимо и выполняется сразу, без шага подтверждения. Пустая таблица — не ошибка: тот же
ответ с нулём. Аргумент разбирается без учёта регистра.

Сбой БД не рапортуется как успешная очистка: приходит отдельное сообщение об ошибке с усечённой
причиной. Это отличается от `get_top_gaps`, который гасит исключение и возвращает пустой список, —
для чтения это допустимо, для удаления нет: «очищено» на месте несработавшего DELETE оставит админа
в уверенности, что таблица пуста.

## Структура

- **`KnowledgeGapService.clear_all() -> int`** — таблицей `knowledge_gaps` владеет он, рядом с
  `get_top_gaps`. Возвращает `rowcount`, исключение пробрасывает.
- **`SupportCommandHandler.clear_stats()`** — `llm_token_usage` этот класс уже запрашивает напрямую
  в `show_top_stats` и `show_user_stats`, удаление логично там же.
- **`SupportCommandHandler.handle_gaps_command()`** — ветка `/gaps` матчилась строгим `text ==
  "/gaps"`, из-за чего `/gaps clear` проваливался в «Неизвестная команда». Теперь разбирает аргумент
  и делегирует отчёту или очистке.
- **`handle_stats`** — ветка `clear` встаёт перед разбором числа, чтобы `/stats clear` не спорил с
  `/stats 50`.
- **`app/constants.py`** — ключи `bot.stats.cleared`, `bot.gaps.cleared`, `bot.clear.failed`.

`session.execute(delete(...))` типизирован как `Result[Any]`, а `rowcount` объявлен только у
`CursorResult`; DML всегда возвращает именно его, поэтому в обоих местах стоит `cast`.

## Тесты

- `tests/test_knowledge_gaps.py::TestClearingGaps` — счётчик удалённых, пустая таблица, проброс сбоя,
  DELETE именно по `knowledge_gaps`.
- `tests/test_command_handler.py::TestClearingGaps` и `TestClearingStats` — рапорт числа, ноль на
  пустой таблице, сбой не выдаётся за успех, `/gaps` без аргумента остаётся отчётом, `/stats 5`
  остаётся топом, не-админ не чистит ничего.

Тестовый двойник БД в `tests/test_command_handler.py` научен отвечать на DELETE: отдаёт настраиваемый
`rowcount` либо бросает настроенную ошибку.
