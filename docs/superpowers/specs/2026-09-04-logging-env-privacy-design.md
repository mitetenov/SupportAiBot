# Три уровня логирования supportBot через .env

Дата: 2026-09-04. Редакция 2 после уточнения пользователя. Статус: ожидает одобрения этой редакции.

## Цель и область изменений

Дать тестовому боту полный диагностический TRACE и оставить компактный INFO для обычной работы и ERROR только для ошибок. Единственный переключатель подробности — BOT_LOG_LEVEL в .env. Ровно три доступных значения: TRACE, INFO, ERROR. Убрать из предыдущего проекта решения HMAC, псевдонимы, CLI поиска пользователей, режимы приватности, отдельный content gate, отдельный уровень зависимостей и настройку формата/обрезки.

Область реализации — Python-процесс supportBot и все его границы взаимодействия: Telegram Bot API, LLM-провайдеры, MCP-серверы, прямой Bedolaga API, входящие webhook, RAG/embedding и PostgreSQL. Журналируется обмен со стороны бота; внутренние запросы MCP-сервера к панели, не проходящие через бот, и журналы других контейнеров этим переключателем не управляются. Не изменять mcp-remnawave и bedolaga-mcp в соседних репозиториях.

Не менять бизнес-логику, отправляемые пользователю или оператору сообщения, историю, prompt, retry/fallback, MCP lifecycle и подпись webhook. Удаление HMAC относится только к предложенной псевдонимизации логов; существующая проверка подписи Bedolaga webhook сохраняется. Не запускать настоящий бот, production или платные API ради проверок.

## Настройка

BOT_LOG_LEVEL по умолчанию INFO. Принимать TRACE, INFO и ERROR без учёта регистра и с удалением внешних пробелов. Отсутствующая переменная означает INFO, пустая строка и любые другие значения, включая DEBUG/WARNING/CRITICAL, считаются ошибкой конфигурации. Сообщать допустимые значения без вывода .env или секретных входных данных; завершать запуск до сетевых соединений.

Префикс BOT_ предотвращает случайное влияние общей .env Docker Compose на другие сервисы. Изменение применяется после перезапуска процесса. Использовать один читаемый текстовый формат: UTC-время, один из трёх уровней, logger/компонент, имя события, диагностические поля. Вывод в существующий консольный поток, без файловых handlers, ротации и новых зависимостей. Экранировать управляющие символы, чтобы текст сообщения не создавал поддельные записи журнала.

Если переменная уже существует, обновить только её; не менять остальные настройки, не выводить и не копировать файл в worktree, не коммитить .env. В .env.example оставить INFO и описать локальный TRACE и минимальный ERROR.

## Уровни

| Настройка | Что выводится |
|---|---|
| TRACE | Все TRACE-события плюс INFO и ERROR |
| INFO | Все INFO-события плюс ERROR; без подробных payloads и переписки |
| ERROR | Только ошибки; ни INFO, ни TRACE |

TRACE реализуется как уровень стандартного Python logging ниже DEBUG, но в публичном контракте и итоговом журнале используются только TRACE, INFO, ERROR. Существующие application DEBUG/WARNING/CRITICAL перераспределяются по смыслу, а не становятся дополнительными доступными уровнями.

### TRACE — полная диагностика

Полностью журналировать текстовые запросы и ответы без прежней обрезки результата MCP до 2000 символов и без отдельного разрешающего флага. Включать сообщения пользователя и оператора, Telegram updates, исходящие Telegram методы/параметры/ответы, команды и реакции, содержимое batch, историю, отправляемые system/developer/user messages, FAQ-контекст, финальный LLM request body, ответы LLM и возвращаемые провайдером reasoning/tool-call данные, аргументы и результаты MCP, входящие Bedolaga webhook и ответы, прямые Bedolaga API вызовы и RAG запросы/результаты. Не обещать несуществующее скрытое reasoning провайдера: журналировать только реально полученные поля.

Для каждого исходящего вызова фиксировать сервис, метод/операцию, URL с очищенными credentials, query, headers с очищенными секретами, тело запроса, ответ, status, длительность и номер попытки. Включать каждую реальную retry/fallback попытку, ошибочный HTTP ответ, invalid JSON, transport exception, MCP init/list-tools/call-tool/reconnect и возвращаемые ошибки инструментов. Не ограничиваться стандартным httpx access log: он не содержит payloads. MCP trace на уровне логического SDK обмена должен отражать полные доступные параметры и результаты, включая страницы списка инструментов; HTTP/stream детали подключать через поддерживаемые точки расширения без изменения протокола.

Для БД TRACE содержит SQL, параметры и диагностические результаты операций приложения, включая прочитанную историю и RAG-кандидатов. Не потреблять курсоры повторно и не материализовать все строки только ради журнала. Операции и результаты, которые приложение уже получает, фиксируются в соответствующих storage/RAG границах. Не включать SQLAlchemy echo в обход общей системы и не допускать вывода SQL на INFO.

JSON/text-поля с base64, которые уже входят в LLM/API payload, относятся к полному payload и не обрезаются. Для отдельно передаваемых двоичных файлов/потоков достаточно метаданных операции, имени, типа, размера при наличии и результата; сырые байты файла в текстовый журнал не выгружать и потоки ради логирования не вычитывать. Это техническое исключение явно описать в README.

TRACE содержит открытые пользовательские ID, имена и содержимое переписки, поэтому предназначен для локальной отладки тестового бота. Запросы логирования не изменяют/не редактируют реальные отправляемые payloads. При INFO/ERROR дорогостоящая сериализация TRACE и копирование больших тел не выполняются.

### INFO — события работы без содержимого обращений

Обязательные события:

- Старт приложения, завершение и ключевые этапы готовности/отключения компонентов.
- Выбранный LLM provider, model, configured effort и фактический effort/режим, реально отправляемый конкретному провайдеру. Если effort не передаётся или не поддерживается, это явно указывается; не выдавать общее значение Settings за фактическое. Аналогичная информация при переключении fallback.
- Переключение fallback: исходная и новая модель/провайдер, причина безопасным кодом/типом, эффективный effort новой цели. Это INFO-событие; сама предшествующая ошибка отдельно относится к ERROR.
- Факт обращения к MCP: сервер, операция/название инструмента, исход, длительность. Аргументы, ответ и пользовательское сообщение здесь отсутствуют.
- Факт запроса к RAG: тип поиска/операция, количество найденных кандидатов, исход и длительность. Текст запроса, embeddings, содержимое FAQ-контекста и результаты здесь отсутствуют.
- Описание загруженных инструментов: сервер, имя и полное описание каждого загруженного инструмента при init и изменении набора после reconnect. Видимый модели набор отражает router allowlist/collision filtering; явно различать загруженный и доступный модели инструмент. Полная input schema относится к TRACE. Не повторять описания при каждом tool call.

Прочие существующие записи распределить по смыслу: готовность/восстановление MCP и значимая смена состояния относятся к INFO, routine шаги обработки конкретного сообщения, cache/buffer/typing и payloads — к TRACE, реальные ошибки — к ERROR. Планирование retry и штатная деградация/ограничение могут быть INFO с безопасной причиной; не превращать штатный fallback, rate limit или ожидаемое отсутствие необязательной записи в ошибку.

На INFO не выводить персональные ID, имена, названия пользовательских топиков, имена вложений, email/IP, тексты переписки, тела запросов/ответов или SQL parameters. Инструментальные описания — метаданные инструментов, а не персональные ответы инструмента. Секреты в метаданных тоже скрывать.

### ERROR — только ошибки

Фиксировать неуспешные операции, включая фактическую ошибку отдельной попытки с последующим retry/fallback, сбои сети/БД/LLM/MCP, отклонённый malformed webhook, неверную конфигурацию и ошибки отправки/обработки. Фатальные ошибки также выводятся как ERROR. Штатная остановка и отмена задач при ней не являются ошибками.

ERROR содержит компонент, операцию, понятную безопасную причину, exception class, error code/HTTP status при наличии и сведения о месте ошибки. Полные response bodies, user messages, SQL parameters и произвольный exception text относятся к сопутствующему TRACE, поскольку сами могут содержать персональные данные. Ошибка, находящаяся в обёртке или возвращённая MCP через is_error, не должна исчезать из ERROR; при этом не дублировать одну и ту же ошибку на каждом уровне стека без дополнительного смысла.

Сохранять полезные безопасные кадры стека (файл/функция/строка), не выводя locals и строки исходного кода. TRACE может содержать полный exception text и cause/context/ExceptionGroup с очисткой credential secrets.

## Контекст и сторонние logger

Простой случайный correlation ID связывает записи одного Telegram batch, Bedolaga ticket turn или операторского /ask. Это ID операции, а не псевдоним пользователя. Он доступен на всех уровнях, наследуется связанными async-вызовами и сбрасывается в finally, включая ошибку/отмену. Отдельные request/attempt ID позволяют сопоставить пары запрос–ответ при параллельных вызовах. Долгоживущий MCP worker не должен наследовать контекст первого обращения навсегда.

Единая конфигурация управляет сторонними logging logger в процессе supportBot. Их DEBUG/INFO и диагностические WARNING, способные содержать payload/URL/ID, нормализуются в TRACE; error/critical нормализуются в ERROR с безопасной сводкой и детальным TRACE. Служебные INFO, требуемые пользователем, создаёт приложение явно. Это не добавляет отдельный переключатель библиотек. Не настраивать только root level, оставляя обход через дочерние handlers. Повторный setup не дублирует handlers/записи; при перенастройке пороги и маршрутизация обновляются.

## Очистка секретов и ошибки вывода

Не вводить режимы приватности, HMAC или дополнительные фильтры содержимого по .env. При этом Telegram bot token, API keys, Authorization/cookie headers, пароль БД, URL userinfo и секретные query credentials не нужны для диагностики и скрываются на любом уровне, в том числе TRACE. Известные credential values из Settings очищаются также в строках/исключениях; чувствительные структурированные ключи обрабатываются рекурсивно. Обычные персональные данные в TRACE не маскируются.

Очистка работает с копией для журнала и не меняет исходный объект, подпись webhook, SQL/HTTP запрос или ответ пользователю. Не сериализовать Settings целиком. Bootstrap/configuration errors до полной настройки не должны раскрывать env input_value. Ошибки formatter, сериализации и обработки неизвестных объектов завершаются безопасным маркером, а не logging error с сырым LogRecord на stderr. Не выводить локальные значения объектов через repr как fallback.

## Проверка и приёмка

Проверять реальные итоговые строки и достижимость событий на mocks, а не только вызовы logger. Для каждой группы событий таблица включает конфигурации TRACE, INFO и ERROR. Итоговые labels — только эти три, пороги кумулятивны. TRACE действительно содержит полные длинные тексты и nested payloads; INFO показывает все перечисленные рабочие события и ERROR; ERROR показывает только реальные ошибки. На INFO/ERROR отсутствуют синтетические персональные данные и content даже в исключениях и сторонних логах; credential secrets отсутствуют на всех уровнях.

Проверить все четыре LLM-провайдера, фактический effort каждого, fallback/retry, MCP init/list-tools/call/reconnect/filtering, Telegram вход/выход, Bedolaga direct API/webhook, RAG/embedding и SQL. Покрыть успех, invalid JSON, не-2xx ответ, timeout, is_error MCP и malformed webhook. Проверить сохранение исходного payload/stream и отсутствие лишних запросов/ретраев. Проверить async-корреляцию, повторный setup, malformed formatting и безопасный отказ на неверной env. Полный offline pytest, минимум покрытия 85%, ruff check, ruff format check, mypy согласно CI.
