Reference source: commit `62f690fd92cd2c024045e94232a1dff2ce388f3e`. The Python source and tests stay in the repository as the behavioral reference. This document records local implementation evidence; it does not establish production or paid-provider equivalence.

## Verified execution

The following command passed on 2026-10-20 against an isolated Docker PostgreSQL 17.11 / pgvector 0.8.7 instance. Tests create separate disposable schemas. `SUPPORTBOT_TEST_DATABASE_URL` must point to a disposable test database; no application `.env` is read by these tests.

  go test -race ./cmd/supportbot ./internal/bot ./internal/bedolaga ./internal/telegram ./internal/storage -count=1

The startup test uses the actual Go composition root, native MCP SDK, PostgreSQL migration, FAQ indexing, Telegram update routing, both health routes, and graceful shutdown. ## Operational diagnostics

`BOT_LOG_LEVEL` controls the existing INFO/ERROR/TRACE behavior. Telegram and Bedolaga HTTP request/response diagnostics are opt-in TRACE, using the shared recursive sanitizer and operation/correlation/request IDs. Photo/PDF bodies are not logged; multipart and download records carry metadata. Default ERROR records expose operation, status and error class rather than private bodies. Runtime startup, health server, command registration and shutdown have operational INFO reports. Root contexts cover Telegram updates, user turns, operator asks, ticket turns and webhooks. `TestTelegramDiagnosticsRespectLevelCorrelationAndSecrets` and `TestBedolagaDiagnosticsRespectLevelAndSecrets` inject sentinel private text and credentials, proving private request/response content stays out of INFO, secrets stay redacted at TRACE, and request/correlation IDs are present.

There is no application file rotation in the Python baseline: both implementations write console logs. Retention jobs preserve the baseline hourly history, 10-minute rate cache, 15-minute conversation state and configured ticket sweep intervals.

## Corrections that restore Python parity

The following were mistakes or omissions in the initial Go port and were corrected to match Python: `/gaps` default15; unnamed topic fallback `User <id>`; exact Telegram command descriptions; MIME-dependent in-memory photo filenames; HTML attribute escaping as `&quot;`/`&#x27;`; startup alerts for MCP initialization failure, tool-name collisions and zero allowed tools; history DB failures preserving an in-memory answer. These are parity fixes, not new product behavior.

## Intentional deviations from the pinned baseline

The changes below were checked against the actual unchanged Python source. Despite appearing as implementation-review findings, the first three are also literal baseline behavior changes: Python `/start` does not discard the pending buffer, and Python `forward_ticket_media` returns a topic ID after an upload/descriptor failure, which advances the mirrored watermark. They are therefore explicitly distinguished from the port corrections above. These changes preserve the already intended reset/operator/retry invariants:

1. A Telegram answer completed after an operator took ownership is suppressed before delivery. Python checked only before the LLM call; Go checks again before send. Test: `TestOperatorTakeoverDuringModelGenerationDropsStaleTelegramAnswer`.
2. `/start` discards that user's pending coalescing buffer before clearing history/transient state. Python cleared history/state but could later answer the old pending question. Test: `TestStartDiscardsPendingUserBurst`.
3. A failed media upload or descriptor warning no longer advances the mirrored-media watermark. Python's forwarder returned a topic ID even on a failed delivery, which marked the attachment complete. Go returns failure, preserves pending state, and retries after restart even when the ticket is answered. Test: `TestRealDBFailedMediaRemainsRetryableAfterAnsweredRestart`.
4. Unknown-size Telegram media streams have a hard bound that raises an error rather than silently truncating an upload. Declared-size behavior remains the original50MiB limit.
5. Remnawave tools taking an internal `userId` verify that ID against the authenticated conversation user's pinned Telegram lookup. A model-supplied foreign ID is refused; valid own-account/operator-assisted scenarios remain available. Literal Python forwarded the model's `userId`; this is an explicit security correction, tested by the native router's foreign/own ID cases.
6. A failed embedding-model replacement retains safe full-text retrieval while disabling incompatible vector search. Python left retrieval unready on that initialization failure. Existing rows/fingerprint are preserved, and a later startup retries. `TestRealHybridInitializerRestartAndAtomicFailure` checks the retained data and degradation.

A post-LLM operator takeover suppresses delivery, but the normal LLM client has already saved that completed turn to history. This preserves the baseline history architecture; an unsent answer may consequently remain in later model context. No two-phase history commit or paid-call cancellation mechanism was introduced.

No additional ban rule, chat allowlist, or product policy was introduced. No separate ban mechanism exists in this baseline.

## Independent review

The architecture agent reviewed the Telegram/ticket/runtime implementation. Corrections included failed-media watermark handling, operator stale-response guard, buffer reset, `/gaps` default15, unnamed topic titles, and exact Telegram command descriptions. The parity agent reviewed LLM/MCP orchestration and found that a history DB outage could turn a successful model reply into an error; the storage owner corrected this and added `TestHistoryDatabaseOutageKeepsConversation`, then it passed in the local real-DB race run.

## External boundary

No production database, Telegram conversation, paid LLM, live cabinet reply, deployment, webhook registration, remote rollout, PR, merge, or commit was performed by these checks. Local HTTP fixture success cannot prove paid-provider behavior, production permissions, or end-user delivery. The existing supportBot source checkout was kept separate from the implementation clone.

Shutdown retains the architecture of bounded polling-handler wait followed by buffer/ticket drain and dependency cleanup. A handler that exceeds the polling shutdown bound may finish only after root work cancellation; exhaustive proof that every possible stuck handler stops before dependency closure is outside the current fixture coverage. No new shutdown architecture was introduced in the operational logging pass.
