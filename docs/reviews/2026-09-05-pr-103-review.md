## Исправления по ревью

Все пять замечаний исправлены в следующем обновлении этой ветки:

1. Снимок истории хранится в формате `role/content`; Gemini преобразует его в `role/parts` при построении своего запроса. Проверены реальные fallback-переходы Gemini → DeepSeek и DeepSeek → Gemini с непустой историей и единственной записью успешного хода.
2. Initializer отключает vector search до проверки fingerprint или полного успешного обновления. При несовместимом или неизвестном индексе доступен FTS без вызова query embeddings. Успешное повторное обновление возвращает vector search.
3. Поисковый запрос собирается из текущего сообщения и цепочки связанных пользовательских реплик до исходной проблемы. Используется уже загруженная история, включая восстановленную после перезапуска. Явный самостоятельный вопрос начинает новую цепочку.
4. Исключение статьи по первому месту в retrieval удалено. `record_faq_context` принимает явно подтверждённые `used_questions` и проверяет их наличие среди кандидатов. Обычные текстовые ответы такой атрибуции не содержат, поэтому автоматически статьи не исключают. Автоматическое извлечение использованных шагов из ответа модели этим изменением не добавлено.
5. Пустой список теперь атомарно удаляет старые FAQ; ошибка очистки не позволяет сохранить новый fingerprint.

Регрессионные проверки включены в `tests/test_pr103_regressions.py`. После исправлений: **1548 passed**, покрытие **89,13%**; Ruff, форматирование изменённых Python-файлов, mypy и `git diff --check` пройдены. Проверки выполнялись с подставными API и хранилищем, без внешних моделей и PostgreSQL.

Границы: определение связанных реплик остаётся эвристическим и ограничено сохраняемой историей; полноценная структурированная диагностика и измерение production accuracy не добавлены. Таблица ниже описывает исходный commit, а не статус исправленного обновления.

## Замечания

### 1. P1 — Общая история fallback содержит формат первого провайдера

Место: `app/llm/base.py:236`, `app/llm/base.py:277`.

`prepare_turn()` сохраняет результат виртуального `_get_conversation_history()` в общий `LlmTurnState.history`. Для Gemini этот метод возвращает `role=model` и `parts`, для DeepSeek/OpenAI-совместимых клиентов — `role=assistant` и `content`. Затем `do_chat()` передаёт сохранённую историю любому резервному клиенту без преобразования.

При непустой истории и переходе Gemini → DeepSeek резервный запрос содержит `parts` и `model`; при обратном переходе Gemini получает `content` и `assistant`. Формат запроса не соответствует API назначения, поэтому исправный резервный провайдер не сможет нормально обработать продолжение. На первом обращении с пустой историей проблема не проявляется.

Это новая регрессия: до PR каждый клиент получал историю через свой метод. Исправление: хранить один снимок в нейтральном формате и преобразовывать его при построении запроса конкретного провайдера. Добавить проверки обоих направлений fallback с непустой историей.

### 2. P2 — После неудачной смены embedding-модели используются несовместимые векторы

Место: `app/rag/service.py:429`, `app/rag/initializer.py:93`.

При отличающемся fingerprint и неполном новом наборе `replace_faq_batch()` сохраняет старые строки. Однако initializer всё равно вызывает `mark_ready()`, а `search()` строит запрос уже текущим embedding-провайдером. Если batch-запрос не удался, но одиночный запрос работает, новая модель сравнивается со старыми векторами. Одинаковая размерность скрывает проблему от PostgreSQL: выдача может выглядеть успешной, оставаясь нерелевантной.

Сохранение старых строк полезно, но не гарантирует совместимость. Нужно отдельно хранить версию активного векторного представления и разрешать vector search только при её соответствии query-провайдеру. При несовместимости до успешной переиндексации использовать FTS либо совместимый старый провайдер. Это недоработка пункта 5 исходного ревью.

### 3. P2 — Второй отказ по-прежнему теряет исходную проблему

Место: `app/llm/base.py:241`, `app/llm/base.py:478`.

`force_context=True` соединяет только последнее пользовательское сообщение с текущим. Последовательность «Все серверы n/a, VPN не работает» → «Не помогло, у меня Android» → «Всё ещё не работает» на третьем ходе даёт поисковый запрос `Не помогло, у меня Android Всё ещё не работает`. Факт `Все серверы n/a` уже отсутствует. История остаётся у LLM, но FAQ подбирается до ответа по неполному запросу.

Первое уточнение теперь сохраняется, однако сценарий двух последовательных отказов из пункта 1 исходного документа не исправлен. Нужен контекст текущей проблемы с накоплением фактов либо сбор запроса из нескольких связанных ходов. Проверять минимум три пользовательских сообщения и последующую смену темы.

### 4. P2 — Исключается первый кандидат FAQ независимо от использованной инструкции

Место: `app/storage/chat_history.py:156`.

`reject_last_faq()` добавляет `context.best_question` в исключения. Это первый результат retrieval, а не статья, выбранная моделью. При кандидатах A/B и ответе по B следующий отказ исключает A и оставляет B: уже не помогшая инструкция доступна для повтора, а альтернативная статья исчезает. Аналогичная проблема возникает после уточняющего вопроса, когда ни одна инструкция ещё не предлагалась.

Это частичное исправление прежнего исключения всех кандидатов. Для завершения пункта 1 нужно фиксировать реально использованные статьи или шаги в результате ответа; при отсутствии подтверждения использования не исключать кандидата автоматически. Новый тест PR с ответом «Какая операционная система?» закрепляет исключение статьи, хотя инструкция в ответе не использована.

### 5. P2 — Пустой FAQ сохраняет старые ответы под новым fingerprint

Место: `app/rag/service.py:425`, `app/rag/initializer.py:98`.

Для валидного источника `[]` метод `replace_faq_batch([])` возвращает `0` без удаления старых строк. Initializer считает `0 == len(usable)` успешной индексацией и сохраняет fingerprint пустого файла. На следующем запуске fingerprint совпадает, старые строки имеют embeddings, и переиндексация пропускается. В результате удалённые из источника инструкции продолжают выдаваться неограниченно долго.

Нужно определить явную семантику пустого источника: либо атомарно очищать индекс, либо отклонять обновление без записи нового fingerprint. До PR `clear_faq()` удалял старые строки и для пустого набора.
