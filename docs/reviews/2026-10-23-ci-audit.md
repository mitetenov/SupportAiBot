# CI audit and optimization — 2026-10-23

Scope: all workflows, CI helpers, Dockerfile, Docker context and validation commands in **SupportAiBot**, against current `master` `45fb11a4be28b96e38a3f752245bdd960b2e0d9d`. The sibling MCP repositories and production were not changed. Existing uncommitted work in the original checkout was preserved.

## Baseline and changes

Measured GitHub runs from October 20, after the AMD64-only change:

| Run | Total elapsed, including scheduling | Test job | Image job |
| --- | ---: | ---: | ---: |
| [PR #117](https://github.com/mitetenov/SupportAiBot/actions/runs/39412167513) | 121 s | 88 s | 22 s |
| [Master publication](https://github.com/mitetenov/SupportAiBot/actions/runs/39412658620) | 119 s | 82 s | 30 s |

The test job spent 15–16 s starting PostgreSQL, 3–5 s on vet, 6 s on race tests, 16–17 s on mypy and 27–28 s on Python tests. These stages ran sequentially. The image build step itself took 6 s on the PR and build/push took 10 s on master, with warm layer caches. These two recent runs are examples, not a p50/p95 benchmark; earlier multi-architecture runs are not a comparable baseline.

The existing Dockerfile is already well optimized: static stripped Go binary, non-root scratch runtime, explicit AMD64 platform, separate module/FAQ/binary layers, a restrictive context allowlist and GHA cache in `mode=max`. Changing it without a measured bottleneck would add risk without demonstrated benefit. It is unchanged.

Verified legacy branch protection through the authenticated CLI after the integration returned 403: `test` is required, strict up-to-date checks and admin enforcement are enabled, force pushes and branch deletion are disabled. Required approving reviews are currently zero. This change preserves the exact existing required-check name. The manual Deploy workflow's most recent recorded run was July 6; its old successes do not validate today's image or deployment changes.

Implemented:

- Separate Go, Python and PR image checks run concurrently after diff selection. PostgreSQL starts only for selected Go checks. Race detection, real pgvector initialization, all selected tests, lint, types and the 85% Python coverage floor remain enforced.
- A stable required check named `test` waits for every selected prerequisite, including the PR image. Failures, cancellations and unexpectedly skipped required jobs fail this gate. No workflow-level `paths-ignore` can leave the required check pending.
- Superseded PR runs are cancelled. Master validation runs independently; only version selection plus image publication is serialized. A documentation-only push cannot evict a queued runtime build from a shared workflow concurrency group. Publication keeps a running push intact; GitHub's default concurrency queue may replace an older pending publication with a newer image candidate.
- Publication is skipped for changes outside image inputs. Manual dispatch requests all checks and, on master, a publication.
- Removed Python installation from publication: the pinned Ubuntu 24.04 runner already has `python3` and `tomllib`. Python reference tests use uv's requested Python 3.14 environment. Test Go compiler now matches Docker's 1.27.3.
- Cache mypy's incremental state by Python line, locked dependencies and source content, restoring compatible dependency caches for source changes. Mypy still runs and invalidates changed modules; baseline type checks cost 13–17 seconds without a persisted incremental cache.
- Actions are pinned to verified full commit SHAs, with grouped weekly Dependabot updates. CI has `contents: read`; deployment needs no GitHub token permissions. Checkout does not persist credentials. Every job has a bounded timeout and the runner OS is explicit.
- Deployment validates the tag before inserting the validated output into SSH commands. Shell metacharacters, newlines and invalid/overlong Docker tags are rejected. Concurrent deployments are serialized. No deployment was executed.

Selection uses `push.before..tested_sha` for pushes and the PR base versus the **tested merge revision** for PRs. It examines the complete range, deletions and both sides of renames. Missing history, initial pushes, manual events and unknown paths request full checks. A failure of the selector itself fails the required gate.

| Changed inputs | Go + PostgreSQL | Python reference | PR image / master publication |
| --- | --- | --- | --- |
| Runtime `cmd/`, `internal/`, Go manifests, Dockerfile/context rules | Yes | No | Yes |
| Go tests / `testdata` only | Yes | No | No |
| `app/`, Python tests, `uv.lock` | No | Yes | No |
| `pyproject.toml`, including release major | No | Yes | Yes |
| FAQ and its assets | Yes | Yes | Yes |
| `docs/`, README, license | No | No | No |
| CI, scripts, unknown future paths | Yes | Yes | Yes |

Resource savings depend on the change mix: runtime-only work avoids the Python environment/type/reference suite; test-only and documentation work avoids image construction and publication. Full changes still run all gates. Parallel execution reduces critical-path latency but adds runner startup and aggregation overhead; it does **not** guarantee fewer total runner-seconds or billed minutes for full changes. No numerical speedup is claimed before live measurement. Caches remain accelerators, not a substitute for executing tests (`go test -race -count=1`).

## Remaining improvements, in priority order

| Priority | Improvement | Reason / concrete next step |
| --- | --- | --- |
| P1 | Add production environment protection when approval is required | Branch protection is already strict and enforces `test`, including for admins. Consider at least one required approving review. Configure a protected production environment with deployment branch restrictions and reviewers if release approval is needed; these are repository policy decisions, not settings changed by this PR. |
| P1 | Deploy immutable digests and verify the SSH host | The deployment default is still mutable `latest`; select the tested digest or immutable commit tag, provision a known SSH host fingerprint, and document an explicit rollback to a previous digest. Environment/secret provisioning was not attempted. |
| P1 | Fail closed on registry errors and guard `latest` promotion | The existing overwrite check treats every failed manifest inspection as an unused tag. Distinguish 404 from authentication, throttling and network errors. The publication lock prevents simultaneous version selection; it does not guarantee source-commit order when tests finish out of order. Before promoting `latest`, reject an older revision than the already-published one. Use immutable SHA/digest tags for deployment meanwhile. |
| P1 | Smoke-test the final image before publication | `push: false` verifies construction, not startup, bundled CA files, FAQ assets, UID, read-only filesystem or native healthcheck. Adapt the existing `scripts/parity/docker_smoke.py` harness to an ephemeral CI database and local Telegram/LLM/MCP mocks, then gate publication on that exact image digest. No paid/live API calls are needed. |
| P2 | Automate workflow and dependency security checks | Add actionlint and shellcheck on workflow/script changes; run `govulncheck`, a Python lockfile audit and an image scan on a schedule and dependency changes. Choose an explicit policy for actionable findings rather than silently accepting failures. Add Go/Docker updates to Dependabot in separate groups. |
| P2 | Bound cache drift and measure source rebuilds | Go's cache is already restored by setup-go, and dependency download layers are exported by BuildKit. The compiler **cache mount** is not exported to GHA by default, so a source change on a fresh runner may still compile dependencies. Benchmark a real source-only miss before adding cache-mount export/import: extra archive I/O and cache storage may exceed its benefit for this small image. Pin/update base image digests deliberately and record SBOM/provenance for published digests. |
| P2 | Add Go coverage and scheduled cross-MCP acceptance | The 85% coverage floor applies to the Python reference, not the production Go runtime. Establish Go coverage from a real run before choosing a floor. The two tests using sibling MCP executables are optional and skipped in current CI; add a pinned-version scheduled integration lane without making normal PRs build unrelated repositories. |
| P3 | Track CI health over enough runs | Record p50/p95 elapsed and total runner-seconds, cold/warm cache state, cancel rate, failures and artifact/cache size over 20+ runs. Add a scheduled/manual full run to audit selectors and cache independence. Avoid sharding this ~2-minute baseline or adding larger/self-hosted runners until measurements justify the cost and maintenance. |

## Validation and limits

Local: actionlint 1.7.12, Ruff lint/format, mypy and `git diff --check` passed. Python: **1738 passed**, **89.63% coverage**. Go vet and race tests against a newly created PostgreSQL 17/pgvector container passed: **91 top-level tests + 378 subtests**, with the two optional sibling-executable subtests skipped, matching normal CI prerequisites. The temporary database is removed after validation.

The selector has regression coverage using real temporary Git repositories for multi-commit deletion, cross-domain rename, PR merge/base advancement, missing history and GitHub output generation. Local workflow simulations also rejected failed/cancelled/skipped-required checks and missing selector outputs (9 cases), plus invalid deployment tags (9 cases).

[Initial PR Actions run](https://github.com/mitetenov/SupportAiBot/actions/runs/39858907884) on `9523a172ae1646a13e9906196e328f731be15e4a` passed all five selected jobs. Total elapsed was **109 seconds** versus the 121-second baseline example. This first run populated the aligned Go compiler and image caches: Go 91 s, Python 42 s, image 58 s, selection 5 s and gate 4 s. Aggregate job runtime was 200 s versus 110 s in the warm baseline PR. This is evidence of correct parallel execution, not a fair warm-cache resource comparison. The mypy cache was added afterwards; a warm measurement is still needed.

Publishing, the master push branch, production deployment, production secrets and server behavior cannot be proven by a PR run. No image was published and no remote service was changed as part of this audit.
