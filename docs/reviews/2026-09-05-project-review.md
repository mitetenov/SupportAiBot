## Подтверждённые проблемы и приоритеты

### 1. P1 — При повторном обращении теряются новые факты и исключаются неиспользованные статьи

Места: [prepare_turn](/Users/mikhail/supportBot/app/llm/base.py:226), [сохранение кандидатов как rejected](/Users/mikhail/supportBot/app/llm/base.py:221), [детектор отказа](/Users/mikhail/supportBot/app/llm/rejection.py:61).

После каждого ответа весь список найденных FAQ записывается в rejected, хотя ответ мог использовать только одну статью или вообще содержать уточняющий вопрос. При следующем отказе эти статьи исключаются целиком. Одновременно поисковый запрос заменяется предыдущим сообщением пользователя — новые сведения из текущего сообщения не участвуют в поиске.

Воспроизведено: после «VPN не работает» ответ «Не помогло, у меня Android» запускает поиск только по «VPN не работает» с исключением всех A/B/C из предыдущей выдачи. Следующий отказ ищет уже по «Не помогло, у меня Android», постепенно теряя исходную проблему.

Отдельно `is_rejection('Как подключить другое устройство?')` и `is_rejection('Не только на телефоне')` возвращают `True`: срабатывают подстроки «другое» и «не то».

Исправление: хранить исходную проблему, ОС, приложение, проверенные факты, предложенные шаги и их результаты. Разделить `retrieved_faq_ids`, `used_faq_ids` и `failed_step_ids`. Собирать запрос из исходной проблемы и новых фактов; исключать не всю статью, а уже безуспешный шаг. Для быстрого исправления — сохранять текущее уточнение, сузить детектор отказа и исключать только действительно использованную инструкцию.

Проверка: диалоги с 3–5 ходами, двумя последовательными отказами, новым фактом внутри отказа и сменой темы на другое устройство.

### 2. P1 — FAQ содержит неоднозначные и конфликтующие правила

Места: [автопродление](/Users/mikhail/supportBot/faq/faq.json:270), [отдельная покупка периода](/Users/mikhail/supportBot/faq/faq.json:355), [безлимит](/Users/mikhail/supportBot/faq/faq.json:155), [лимит триала](/Users/mikhail/supportBot/faq/faq.json:198).

Одна статья обещает автоматическое продление при достаточном балансе, другие требуют отдельной покупки периода; системный промпт запрещает обещать автопокупку. Возможно, речь идёт о разных режимах, но условия их применения в FAQ не обозначены. Безлимитный трафик заявлен без оговорки, тогда как другая статья говорит о лимите триала. Названия разделов кабинета различаются: «Баланс и платежи» / «Баланс», «Подписки» / «Подписка».

В [статье про мобильную сеть](/Users/mikhail/supportBot/faq/faq.json:407) причина объявляется установленной только по признаку «работает через Wi-Fi». Это предположение, которое следует проверять диагностикой.

Исправление: сверить бизнес-условия и UI с действующим сервисом; явно описать условия триала, покупки и продления. Хранить канонические названия разделов и правила оплаты в одном месте. Добавить FAQ-поля `id`, `intent`, `platform`, `conditions`, `updated_at`, `source`; проверять противоречия при изменении знаний. Фактическое поведение биллинга в этом ревью не устанавливалось.

### 3. P1 — Отказ эмбеддингов отключает и текстовый поиск

Место: [search](/Users/mikhail/supportBot/app/rag/service.py:398).

Если `embed_query_as_vector()` не вернул вектор, метод завершает работу до SQL. Воспроизведено: для «как оплатить» при пустом ответе embedding-провайдера получен `[]`, число обращений к БД — **0**. Резервный поиск реализован только в обратную сторону: ошибка hybrid → vector.

Исправление: отдельный FTS-only путь, доступный при отказе embedding-провайдера; различать `no_match` и `retrieval_unavailable` в результате. При полном отказе поиска отвечать с учётом недоступности знаний, не выдавать отсутствие контекста за отсутствие информации в FAQ.

Проверка: embedding timeout/429/пустой вектор при рабочей БД, затем отказ обоих источников. Проверять не только выдачу, но и ограничение времени ответа.

### 4. P2 — После перезапуска FAQ ищется до загрузки истории

Места: [порядок prepare_turn и загрузки истории](/Users/mikhail/supportBot/app/llm/base.py:255), [синхронное чтение предыдущего сообщения](/Users/mikhail/supportBot/app/storage/chat_history.py:115).

`prepare_turn()` обращается к памяти до `get_history()`, которое загружает данные из БД. Воспроизведено: сохранён диалог «Все серверы n/a» → «Какая ОС?», после холодного старта пользователь пишет «iOS»; FAQ ищется только по «iOS». Модель позже получает историю, но подбор статей уже завершён.

Исправление: загружать историю до подготовки поиска, передавать один снимок истории в retrieval и LLM. Состояние диагностики также восстанавливать из хранилища.

### 5. P2 — Переиндексация может потерять рабочую базу или сохранить несовместимые векторы

Места: [hash и clear-before-index](/Users/mikhail/supportBot/app/rag/initializer.py:39), [удаление старых записей](/Users/mikhail/supportBot/app/rag/initializer.py:88), [проверка только размерности](/Users/mikhail/supportBot/app/storage/schema.py:132).

Индекс признаётся актуальным по хешу JSON и количеству заполненных векторов. Модель и способ построения embedding не входят в версию индекса. При смене embedding-модели на другую с той же размерностью старые векторы останутся, а запросы будут представлены новой моделью.

Перед созданием новых embeddings удаляются прежние FAQ. При отказе провайдера рабочая база заменяется пустой или частичной; после частичного результата вызывается `mark_ready()`.

Исправление: fingerprint из FAQ, модели, размерности, режима query/document и версии подготовки текста. Сначала строить новый набор, проверять полноту и только затем атомарно заменять активный. До успешного переключения обслуживать старую версию совместимым провайдером.

### 6. P2 — Benchmark неправильно подписывает сравниваемые режимы

Места: [GRID](/Users/mikhail/supportBot/benchmarks/retrieval_benchmark.py:25), [реализации режимов](/Users/mikhail/supportBot/benchmarks/retrieval_benchmark.py:104), [текущий append](/Users/mikhail/supportBot/app/rag/service.py:534).

Режим `compete` вызывает сохранённый production-метод, который уже реализует append. Поэтому `compete` и `append` фактически проверяют одно поведение, а надписи продолжают обещать сравнение старого и нового ранжирования. Baseline отмечает 0,65, тогда как production-порог равен 0,45.

Исправление: явные независимые стратегии, baseline из конфигурации текущей версии, тест с кандидатами, для которых compete и append обязаны дать разный порядок. В отчёт записывать commit, модель embeddings, fingerprint FAQ, конфигурацию и результаты каждого кейса.

### 7. P2 — Перед отправкой нет повторной проверки участия оператора

Места: [начальная проверка](/Users/mikhail/supportBot/app/bot/pipeline.py:84), [отправка после LLM](/Users/mikhail/supportBot/app/bot/pipeline.py:124), [фиксация ответа оператора](/Users/mikhail/supportBot/app/bot/router.py:201).

Если оператор ответит, пока модель генерирует ответ, бот всё равно отправит результат: состояние проверяется только до длительного вызова LLM. Это создаёт параллельные, потенциально противоречивые рекомендации. Наличие ветки подтверждено чтением кода; отдельный конкурентный тест в этом ревью не выполнялся.

Исправление: версия состояния диалога, проверка непосредственно перед отправкой и согласование с записью истории. Явное состояние handoff при запросе человека позволит не ждать первого ответа оператора для подавления AI.

### 8. P2 — Статистика knowledge gaps не различает причины ошибок достаточно точно

Места: [порядок причин и порог 0,72](/Users/mikhail/supportBot/app/rag/knowledge_gaps.py:167), [max_similarity по всем поискам](/Users/mikhail/supportBot/app/rag/service.py:592).

`LOW_SIMILARITY` имеет приоритет над явной эскалацией. Успешный персональный ответ через MCP без FAQ становится `NO_MATCH`. Максимальная similarity может относиться к результату канонического fallback-запроса, а не пользовательскому вопросу. Поэтому текущие /gaps полезны для просмотра, но не являются измерением точности ответа.

Исправление: хранить независимые признаки — доступность retrieval, релевантность основной выдачи, использованные FAQ и MCP, причина эскалации, результат обращения. Калибровать порог по размеченным запросам каждой embedding-конфигурации.

## Повышение точности после исправления ошибок

1. **Состояние диагностики:** исходная проблема, ОС, приложение, источник оплаты, выполненные шаги и их результаты. Для оплаты и проверки доступа — явные обязательные переходы и проверенные факты. LLM формулирует ответ на основе этих данных.
2. **Проверяемый результат модели:** кроме текста возвращать использованные FAQ ID, ссылки на факты текущего MCP-хода, недостающие сведения и причину эскалации. Валидировать существование и применимость источников. Одни только ID не доказывают истинность утверждений; важны содержательные проверки.
3. **Embeddings для query/document:** текущий Gemini-провайдер не разделяет режимы. Для используемой `gemini-embedding-001` сравнить `RETRIEVAL_QUERY` и `RETRIEVAL_DOCUMENT`, предусмотренные [официальной документацией Gemini](https://ai.google.dev/gemini-api/docs/embeddings). Вместе с этим обновить интерфейс, ключи кэша и fingerprint индекса. Улучшение качества должно быть подтверждено экспериментом.
4. **Фильтрация по ОС и намерению:** применить метаданные FAQ, затем сравнить reranking кандидатов на сложных запросах. Дополнительный модельный вызов оправдан только при измеримом выигрыше качества относительно задержки и стоимости.
5. **Скриншоты:** [MessageBatch.of](/Users/mikhail/supportBot/app/bot/buffer.py:73) передаёт модели только первое изображение пачки. Для обращения «скрин оплаты + скрин ошибки» сохранять оба в рамках установленного лимита. Извлечённый код ошибки/название приложения использовать для дополнительного поиска FAQ; сейчас retrieval строится до разбора изображения.
6. **Контроль качества:** 38 retrieval-кейсов, из них 9 отрицательных, и 13 behavioral-кейсов — полезная отправная точка. [Behavioral evaluator](/Users/mikhail/supportBot/benchmarks/agent_behavior_eval.py:274) подставляет кандидатов FAQ, поэтому не проверяет всю цепочку поиска и ответа. Добавить отдельный сквозной набор с настоящим retrieval, синтетическими MCP и размеченными ожидаемыми решениями.

## Порядок внедрения и измерения

1. Исправить историю, отказы, противоречия FAQ и FTS-only деградацию. Добавить регрессии на описанные сценарии.
2. Исправить benchmark, подготовить независимый набор диалогов и замерить текущую систему. Отделить данные настройки от окончательной проверки. Начать со 100–200 обезличенных обращений, включая ошибки оплаты, ОС, смену темы, неточный ввод, отсутствие источников и эскалацию; это предлагаемый объём, не требование.
3. Внедрить атомарную индексацию, deadline, общую конкуренцию и корректный handoff.
4. По одному сравнивать task-aware embeddings, метаданные, reranking и модели. Сохранять только улучшения, которые проходят один и тот же набор.

Метрики: правильное решение по разметке оператора; доля неподтверждённых утверждений; правильность и порядок MCP-вызовов; повтор уже не помогшего шага; оправданность эскалации; retrieval hit@1/recall@k и ложные совпадения; p50/p95; токены и стоимость успешно решённого обращения. Снижение числа эскалаций само по себе не считать улучшением.
